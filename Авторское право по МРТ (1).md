## **Область применения**

BuhPro представляет собой цифровую платформу, предназначенную для организации и контроля взаимодействия между заказчиками бухгалтерских услуг, профессиональными исполнителями, наставниками обучающих курсов и администраторами системы. Программа относится к области web-платформ для деловых услуг, однако ее функциональное назначение шире, чем у обычной доски объявлений. Проект исследует и автоматизирует полный жизненный цикл бухгалтерской услуги: от момента формулирования задачи заказчиком до выбора исполнителя, коммуникации, завершения работы, отзыва, обновления рейтинга и, при необходимости, профессионального обучения специалиста.

Предметная область программы связана с рынком бухгалтерского аутсорсинга. В этой сфере качество услуги зависит не только от профессиональных навыков исполнителя, но и от ясности постановки задачи, прозрачности коммуникации, своевременного контроля статусов, возможности сравнения откликов и наличия репутационного механизма. В традиционной модели эти элементы часто разнесены по разным каналам. Заказчик может публиковать запрос в мессенджере, получать неформальные ответы, обсуждать детали в личной переписке, передавать документы через отдельные сервисы и оценивать результат устно. В результате процесс становится трудно проверяемым, история решений фрагментируется, а качество работы исполнителя не связывается с его дальнейшим профессиональным развитием.

BuhPro решает эту проблему путем создания единой информационной среды, в которой бухгалтерская услуга представлена как структурированный цифровой процесс. Каждое значимое действие получает формальное состояние, каждый участник действует в рамках определенной роли, а система хранит историю заказов, откликов, чатов, платежей, отзывов, санкций, уведомлений и обучающих назначений. Поэтому программу можно рассматривать не только как практическую платформу для размещения бухгалтерских задач, но и как программную модель исследования цифровой организации доверия в профессиональных услугах.

Объектом исследования, реализованным в программе, является процесс взаимодействия между заказчиком и исполнителем бухгалтерской услуги. Предметом исследования выступает совокупность программных механизмов, делающих это взаимодействие управляемым: ролевая модель доступа, жизненный цикл заказа, жизненный цикл отклика, имитация платежных состояний, выбор исполнителя, внутренняя коммуникация, пересчет рейтинга, санкции и образовательное сопровождение. Практическая цель проекта состоит в снижении неопределенности на рынке бухгалтерских услуг и предоставлении участникам предсказуемого цифрового процесса.

Со стороны заказчика центральной функцией программы является создание заказа. Заказчик описывает задачу, выбирает категорию услуги, указывает бюджет, регион и ожидаемый срок выполнения, после чего получает рассчитанную стоимость размещения. Такой интерфейс заставляет формулировать задачу структурированно. В результате исполнитель получает не абстрактное сообщение, а формальное описание бизнес-проблемы, например ведение бухгалтерии для ТОО, налоговую оптимизацию для ИП, подготовку финансовой отчетности или внутренний аудит.

Рисунок 1. Создание заказа заказчиком и расчет стоимости размещения

Форма создания заказа важна потому, что она преобразует бизнес-потребность в данные, которые могут быть обработаны системой. Название дает короткую смысловую метку запросу. Категория позволяет выполнять фильтрацию и последующую статистическую группировку. Описание передает контекст исполнителю. Бюджет задает экономические рамки задачи. Срок показывает временное ограничение, а регион уточняет, может ли услуга быть выполнена удаленно или требует локального знания. Эти поля поддерживают как практическое использование, так и аналитическую интерпретацию активности платформы.

После создания заказ отображается в личном кабинете заказчика. Кабинет разделяет активные заказы, заказы в работе и завершенные заказы. Он также отделяет черновики от опубликованных заказов, что важно для сохранения естественной последовательности работы. Заказчик может сначала создать черновик, затем уточнить его содержание и только после этого отправить заказ на публикацию. Это снижает риск появления неполных или неточных бухгалтерских запросов в публичной ленте исполнителей.

Рисунок 2. Личный кабинет заказчика со списком заказов

Личный кабинет также выполняет функцию мониторинга. Он дает заказчику компактное представление о текущем состоянии сотрудничества с исполнителями. Вместо поиска информации в отдельных чатах или документах пользователь видит все релевантные заказы в одном интерфейсе. Это особенно важно для бухгалтерских услуг, поскольку один и тот же заказчик может одновременно нуждаться в налоговой консультации, финансовой отчетности, сопровождении бухгалтерского учета и аудиторской помощи. Таким образом, платформа поддерживает параллельное управление несколькими запросами.

Редактирование заказа реализовано через модальное окно. Это проектное решение имеет практическое значение: заказчик может исправить название, описание и бюджет, оставаясь в контексте списка заказов. Программа поддерживает итеративный подход к постановке задачи. В реальной бухгалтерской практике требования часто становятся понятнее только после того, как заказчик начинает их формулировать. Возможность уточнить заказ до финальной отправки делает платформу ближе к реальному процессу принятия решений.

Рисунок 3. Редактирование параметров заказа в личном кабинете заказчика

Со стороны исполнителя платформа исследует другую часть процесса: поиск, фильтрацию и принятие решения перед отправкой отклика. Исполнитель может просматривать опубликованные заказы, фильтровать их по категории, городу и ключевым словам, а также сортировать по новизне. Каждая карточка заказа содержит бюджет, дату публикации, категорию и краткое описание. Это позволяет исполнителю оценить, является ли задача экономически привлекательной и соответствует ли она его компетенции.

Рисунок 4. Поиск и фильтрация опубликованных заказов исполнителем

Интерфейс поиска является ключевым элементом платформы, потому что он превращает общий marketplace в специализированную профессиональную среду. Налоговый консультант может сосредоточиться на налоговых запросах, бухгалтер — на задачах ежемесячного учета, аудитор — на заданиях, связанных с проверкой отчетности. Таким образом, программа поддерживает не только наличие заказов, но и соответствие содержания бухгалтерской задачи профессиональному профилю исполнителя.

Личный кабинет исполнителя дополняет поиск заказов аналитикой собственной активности. В нем отображаются рейтинг, количество откликов, активные работы, завершенные задачи, данные профиля и показатели производительности. Эта часть системы выполняет репутационную функцию. Исполнитель не просто отправляет предложения: его действия становятся измеримыми показателями, влияющими на доверие. Для заказчика рейтинг и отзывы становятся дополнительным основанием выбора специалиста. Для исполнителя кабинет становится механизмом обратной связи, показывающим, как профессиональная активность отражается в системе.

Рисунок 5. Личный кабинет исполнителя с заказами, рейтингом и показателями производительности

Роль рейтингов в BuhPro не ограничивается отображением числа. Платформа связывает рейтинги с более широким процессом контроля качества. После завершения заказа заказчик может оставить отзыв. Отзыв влияет на профиль исполнителя, а низкие оценки могут приводить к санкциям или назначению обучающих курсов. Такое решение важно, потому что создает замкнутый контур качества. Система не только фиксирует слабый результат, но и может инициировать корректирующий образовательный путь.

Коммуникация между участниками реализована в отдельном модуле чатов. Чат связан с конкретным заказом, что отличает его от обычного мессенджера. Обсуждение остается привязанным к бизнес-контексту, а каждая переписка относится к определенной задаче. В текущей реализации модуль чатов основан на REST API и включает историю сообщений, управление состоянием прочтения и контроль доступа участников. В результате формируется проверяемый канал коммуникации между заказчиком и исполнителем.

Рисунок 6. Интерфейс чата между участниками заказа

Модуль чатов особенно важен для бухгалтерских услуг, потому что детали задачи часто требуют уточнения. Исполнителю могут понадобиться дополнительные документы, пояснения о бизнес-обороте, налоговом режиме, прошлых отчетных периодах или сроках. Когда такая коммуникация хранится в той же платформе, что и заказ, взаимодействие становится легче отслеживать и проверять. Это снижает риск потери важной информации и повышает ответственность сторон.

Отдельным направлением проекта является обучение и развитие компетенций. В платформе предусмотрена роль наставника, который управляет образовательными курсами. Панель наставника показывает количество курсов, число опубликованных курсов, процент завершения, черновики и популярные курсы. Этот компонент связывает marketplace-логику с образовательной подсистемой. Платформа не только распределяет бухгалтерские задачи, но и поддерживает рост профессиональных компетенций.

Рисунок 8. Предварительный просмотр создаваемого обучающего курса

Внутренняя логика BuhPro построена вокруг нескольких взаимосвязанных сущностей. Заказ может проходить состояния черновика, ожидания оплаты, публикации, работы, завершения или отмены. Отклик исполнителя также имеет собственный жизненный цикл: черновик, ожидание оплаты, отправленный отклик, принятие, отклонение или отмена. Платежные транзакции фиксируют экономический этап публикации заказа или отправки отклика. Когда заказчик выбирает исполнителя, выбранный отклик принимается, остальные отклики отклоняются, а заказ переходит в работу. После завершения заказчик может оставить отзыв, и этот отзыв влияет на рейтинг исполнителя.

Такой жизненный цикл важен для исследовательской ценности программы. Он позволяет представить каждое бизнес-событие как переход между состояниями, а не как неформальное действие. Например, публикация заказа — это не просто появление карточки на странице, а результат валидации, обработки платежного состояния и перехода от подготовки к публичной доступности. Аналогично выбор исполнителя — это не только нажатие кнопки, а изменение состояния заказа, состояния откликов и коммуникационного контекста. Такое моделирование делает платформу предсказуемой и пригодной для дальнейшего развития.

Программа также включает подсистему уведомлений. Уведомления создаются при важных событиях: публикации заказа, отправке отклика, выборе исполнителя, завершении заказа, создании отзыва, создании санкции, назначении курса и получении сообщения в чате. Уведомления уменьшают необходимость вручную проверять каждый раздел платформы. С системной точки зрения они также связывают независимые модули в единый процесс. Событие в модуле заказов может создать обновление в модуле уведомлений, сообщение в модуле чатов или назначение курса в обучающем модуле.

Административная роль обеспечивает надзор за платформой. Администраторы могут просматривать заказы, санкции, назначения курсов, уведомления, чаты и другие данные платформы. В производственной среде такие функции необходимы для модерации, анализа спорных ситуаций и операционного контроля. В текущей реализации административный модуль также поддерживает демонстрационные и разработческие сценарии, включая подтверждение платежей для локального тестирования. Это позволяет проверять полный жизненный цикл заказов и откликов без подключения реального платежного провайдера на раннем этапе разработки.

Безопасность и контроль доступа реализованы через аутентификацию, ролевую авторизацию и ограниченные области API. Заказчики могут создавать и управлять своими заказами. Исполнители могут отправлять отклики и управлять своими откликами. Наставники могут создавать и управлять курсами. Администраторы имеют расширенные возможности чтения и контроля. Программа использует JWT-аутентификацию и разделяет публичные и защищенные endpoints. Это важно, поскольку бухгалтерские задачи могут содержать финансовую и коммерчески чувствительную информацию, и каждый участник должен видеть только те данные, которые относятся к его роли.

Backend-архитектура следует многоуровневой структуре. HTTP-handlers принимают и валидируют запросы, service-слой содержит бизнес-правила и проверки доступа, repositories взаимодействуют с базой данных PostgreSQL, а платформенные модули обеспечивают инфраструктурные функции: логирование, метрики, платежи, хранение файлов и миграции базы данных. Такое разделение повышает сопровождаемость программы. Оно также поддерживает исследовательскую цель проекта: отдельные бизнес-процессы можно изучать, тестировать и улучшать без смешивания интерфейсной логики, бизнес-правил и SQL-кода в одном месте.

Frontend-архитектура отвечает за представление той же бизнес-логики разным пользовательским ролям. Пользовательский интерфейс учитывает роль: заказчик видит создание и управление заказами, исполнитель — поиск, отклики и личную производительность, наставник — создание курсов и аналитику, администратор — инструменты контроля. Такой интерфейс важен, потому что одна и та же платформа должна поддерживать разные цели, не перегружая пользователей нерелевантными функциями.

Практическая значимость программы заключается в создании управляемой цифровой среды для бухгалтерских услуг. Для заказчиков BuhPro снижает неопределенность при поиске специалиста, поскольку заказ структурируется, отклики собираются централизованно, а коммуникация привязана к заказу. Для исполнителей система предоставляет стабильный канал поиска работы, формирования репутации и получения обратной связи. Для наставников она предоставляет инструмент публикации и управления образовательным контентом. Для администраторов она обеспечивает наблюдаемость и контроль процессов платформы.

Экономическая значимость платформы связана со снижением транзакционных издержек. Без специализированной системы заказчики тратят время на поиск специалистов, ручное сравнение предложений и поддержание коммуникации во внешних каналах. Исполнители тратят время на поиск подходящих задач и постоянное подтверждение своей компетенции. BuhPro уменьшает эти затраты за счет стандартизации формата заказа, поиска и фильтров, истории откликов и отзывов, а также видимой репутации внутри платформы.

Социальная значимость платформы связана с профессионализацией цифровых бухгалтерских услуг. Малые компании и индивидуальные предприниматели часто нуждаются в бухгалтерской поддержке, но не имеют внутреннего бухгалтерского отдела. Цифровая платформа делает профессиональные услуги доступнее и одновременно дает специалистам возможность предлагать работу в прозрачной среде. Интеграция обучающих курсов дополнительно повышает ценность системы, потому что поддерживает непрерывное развитие, а не только разовый обмен услугами.

На текущем этапе система сфокусирована на основных MVP-процессах: аутентификации, профилях, заказах, откликах, выборе исполнителя, отзывах, рейтингах, санкциях, курсах, уведомлениях, чатах, загрузках файлов и демонстрационных платежных сценариях. Некоторые расширенные производственные функции могут быть разработаны позднее: реальные платежные callback-и, webhooks, realtime-чат через WebSocket, расширенная модерация, детальное разрешение споров, email/SMS-доставка и расширенная аналитика курсов. Эти ограничения не снижают ценность текущей программы, а определяют границы реализованного исследовательского прототипа.

## **Основные технические характеристики, язык программирования и тип реализующей ЭВМ**

**Технические требования к аппаратно-программному обеспечению:**

Клиентская часть программы запускается в современном web-браузере и не требует установки отдельного desktop-приложения. Пользователю необходим персональный компьютер или ноутбук с доступом к Интернету, процессор уровня Intel Core i3 или выше, не менее 4 Гбайт оперативной памяти, монитор с разрешением не ниже 1024x768 и актуальная версия Google Chrome, Microsoft Edge, Mozilla Firefox или Safari. Поскольку платформа является web-приложением, основным требованием для конечного пользователя является стабильный доступ к серверу через браузер.

Серверная часть программы может запускаться на компьютере, локальной машине разработчика или виртуальном сервере с Windows, Linux или macOS. Для локального развертывания используются Docker и Docker Compose, PostgreSQL, backend-сервис на Go и frontend-приложение на Next.js. Рекомендуемые характеристики серверной среды включают x86-64 процессор, не менее 4 Гбайт оперативной памяти и не менее 1 Гбайт свободного места для приложения, миграций, локального файлового хранилища и данных базы. Для более крупных внедрений объем памяти, CPU и хранилища базы данных должны масштабироваться в зависимости от количества активных пользователей, заказов, файлов и сообщений.

**Архитектура программы:**

BuhPro реализована как web-платформа с разделением клиентской и серверной частей. Frontend предоставляет пользовательские интерфейсы для заказчиков, исполнителей, наставников и администраторов. Backend предоставляет REST API, проверяет права доступа, хранит бизнес-сущности, управляет состояниями заказов и откликов, обрабатывает аутентификацию, уведомления, чаты, курсы, рейтинги, санкции и загрузку файлов.

Backend построен по модульной многоуровневой архитектуре. Основные модули включают аутентификацию, профили, заказы, отклики, выбор исполнителя, отзывы, рейтинги и санкции, курсы и назначения курсов, уведомления, чаты, загрузки, вложения, кошельки и разработческие платежные операции. Данные хранятся в PostgreSQL, а структура базы поддерживается файлами миграций. Система использует JSON API responses, пагинацию, request identifiers, логирование, recovery middleware и Prometheus-совместимые метрики.

Программа поддерживает следующие пользовательские роли:

- Заказчик: создает заказы на бухгалтерские услуги, управляет черновиками, публикует заказы, просматривает отклики, выбирает исполнителя, завершает работу и оставляет отзывы.
- Исполнитель: ищет опубликованные заказы, отправляет отклики, общается с заказчиками, выполняет работу, получает рейтинги и отслеживает санкции или назначения курсов.
- Наставник: создает и управляет обучающими курсами, публикует учебный контент и отслеживает показатели, связанные с курсами.
- Администратор: наблюдает за активностью платформы, просматривает системные данные, управляет санкциями, уведомлениями, назначениями курсов и разработческими платежными сценариями.

Основные потоки данных платформы включают:

- Поток заказа: создание черновика, редактирование, отправка, состояние ожидания оплаты, публикация, выбор исполнителя, работа, завершение или отмена.
- Поток отклика: черновик исполнителя, отправка, состояние ожидания оплаты, опубликованный отклик, принятие, отклонение или отмена.
- Коммуникационный поток: создание чата, отправка сообщений, чтение сообщений и уведомление второго участника.
- Поток качества: завершение заказа, создание отзыва, обновление рейтинга, создание санкции и возможное назначение курса.
- Образовательный поток: создание курса, публикация, назначение исполнителю и отслеживание завершения.

Такая архитектура делает программу расширяемой. Новые платежные провайдеры, дополнительные каналы уведомлений, realtime-сообщения, расширенные функции курсов или инструменты модерации могут быть добавлены без изменения всей структуры системы.

**Установка, запуск и удаление программы:**

Для локального запуска backend необходимо подготовить переменные окружения, запустить PostgreSQL и применить миграции базы данных:

```powershell
Copy-Item .env.example .env
docker compose up -d postgres
make migrate-up
make run
```

Frontend запускается отдельно в каталоге клиентского приложения:

```powershell
pnpm install
pnpm dev
```

После запуска пользователь открывает платформу в браузере по адресу:

```text
http://localhost:3000
```

Backend API по умолчанию доступен по адресу:

```text
http://localhost:8080
```

При использовании Docker Compose backend-сервис, база данных PostgreSQL и дополнительная инфраструктура могут быть запущены одной командой:

```powershell
docker compose up --build -d
```

Для остановки локальной версии программы используется команда:

```powershell
docker compose down
```

Если также требуется удалить постоянные локальные данные базы, Docker volumes могут быть удалены разработчиком или администратором после проверки и резервного копирования.

## **Язык программирования**

Данный программный продукт создан с использованием следующих технологий.

Backend: Go 1.23, web-фреймворк Gin, pgx для доступа к PostgreSQL, JWT для аутентификации, миграции PostgreSQL, структурированное логирование, request middleware, Prometheus-совместимые метрики и Docker-based deployment.

Frontend: TypeScript, React, Next.js, Tailwind CSS, Radix UI, lucide-react, SWR и Firebase Web SDK для клиентских интеграционных сценариев.

База данных и инфраструктура: PostgreSQL, Docker, Docker Compose, локальное файловое хранилище для загруженных материалов и REST API как основной механизм взаимодействия между frontend и backend.

Выбранный технологический стек подходит для проекта, потому что Go обеспечивает высокую производительность и простое развертывание backend-сервисов, PostgreSQL предоставляет надежное реляционное хранилище для заказов, откликов, пользователей и чатов, а Next.js позволяет создавать гибкий web-интерфейс для ролевых пользовательских сценариев. Вместе эти технологии формируют полноценную web-платформу, которую можно запускать локально для демонстрации и расширять для production-развертывания.
